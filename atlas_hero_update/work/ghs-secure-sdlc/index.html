4. Secrets management policy

Architecture decision record summary (accepted): keep credentials out of source control; give the app one secrets abstraction that reads environment variables in every environment.

  • What changed: centralized secrets module reading process environment variables instead of embedding keys in code or committing them.
  • Why: accidental commit of credentials is tracked as a high-impact risk; environments differ (local vs cloud) and should not couple app code to a single vault product.
  • Local: developer environment file, gitignored, never committed.
  • Cloud: managed secret store injects values as runtime environment variables; IAM least privilege; auditability of access.
  • How keys are rotated: operational docs call for a periodic rotation cycle (documented as a 90-day cadence) using the platform secret-set / redeploy path — rotate the store value, then roll the runtime so old material is retired.
  • Supply-chain CI: security workflow builds the backend, emits an SBOM artifact, and runs dependency audit on pushes/PRs.

Lessons learned: secret hygiene

A credential file was found in repository history and is being remediated (history cleanup and key invalidation are in flight / awaiting explicit owner approval for rewrite publication). This portfolio demo deliberately omits paths, project identifiers, and key material. Takeaway for interviews: treat “gitignore alone” as insufficient — scan history, rotate anything that ever touched a shared remote, and prefer short-lived workload identity over long-lived key files.

5. Incident-response tabletop — role change

Simulated SEV-2 scenario (2025-09-24): unauthorized elevation to admin. Personas below are the simulation’s test accounts from the write-up — not real class users.

  1. Triage

    Classify as SEV-2; open a simulated incident channel.

  2. Investigate — traces

    Query the executions audit collection; locate a trace showing a simulated admin account promoted a simulated student account to admin.

    Finding: traces were effective for attribution; request body (target + new role) was missing from the record.

  3. Investigate — auth logs

    Auth logs show a successful login for the admin account from an unrecognized IP shortly before the change — credential compromise hypothesis.

  4. Contain

    Disable the compromised admin account (simulated console action); note refresh-token revocation to kill sessions.

  5. Recover

    Revert the elevated student’s role; force password reset on the admin account.

  6. Lessons / actions

    Keep structured traces; enrich critical audit events with sanitized request bodies; add proactive alerts when admin claims are granted (do not wait for a user report).
